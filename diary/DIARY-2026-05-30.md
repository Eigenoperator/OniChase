# DIARY - 2026-05-30

今天主要是在 V5 ship 交互上做收口，把“船已经可玩”从数据层推进到实际玩家操作不会迷路的状态。

先处理的是高松港和小豆岛相关的问题。Scorp 指出另一个工作区把问题导向 `docs/v4.html`，甚至说要临时 patch 高松港到土庄港 ferry，这是错误方向。重新核对后确认：这件事属于 V5，不属于 v4；V5 里已经有真实官方船班数据，例如 `高松港 -> 土庄港`，不需要伪造临时船。当前工作区也没有改 `docs/v4.html`，没有小豆岛 ferry patch。

V5 里真正的问题有两个。第一，船是短途公共交通，不应该像飞机一样让玩家停在“买票/持票”流程里。已把 `addShipStep()` 后的状态改成：选择船班后直接追加 `TAKE_SHIP`，清空 ship origin/destination 选择，关闭 ship map，并根据船到达侧接续点自动切到下一步模式。到达侧是 rail station 就回 rail，是 bus stop 就进 bus，是 airport 就进 flight。这样玩家选完船后看到的是“从船的终点继续走”，而不是还卡在这趟船上。

第二，runner 到港口或上船后红点看不到，以及高松到小豆岛后看不到小豆岛出发船。根因不是缺船班，而是港口接驳里的 connector-only bus stop 没有进入 `busStopCoordinate()` 的查询索引。像土庄港这种接续点，状态已经是 `BUS_STOP`，但坐标查不到，marker 数据就会空；ship origin 列表也会因为没有当前锚点而退回到旧位置附近排序，看起来像还在高松侧。修复后，port connector bus stop 会被索引进名称和坐标查询；回放 carrier state 在 `WALK_FROM_PORT_TO_STATION` 后也会保留 bus-stop/airport 状态，不再错误落成空 rail node。

为避免“数据源有 marker，但视觉/交互又被改坏”的情况，补了 V5 专用 Playwright 回归：`scripts/tests/v5_ship_interaction_audit.js`。它只走 V5 真实数据，固定使用 `高松港 -> 土庄港` 船班，检查三个关键状态：`PORT_WAIT`、`SHIP`、到达后的 `BUS_STOP` 都有 runner marker 坐标和 map layer feature；同时检查到达后 ship origin 列表第一项是 `土庄港`，并且 `土庄港` 可继续选择至少包含 `高松港` 的出发船。最新输出是安静的一行：

```text
OK v5 ship interaction: markers=3, firstPort=土庄港, onward=4
```

最后把这个测试写进 README 的 Audit And Regression 区，命令也保持安静：本地 server 日志写到 `/tmp/chase_http.log`，测试本身只打印 OK 或失败 JSON。这样另一个工作区如果再碰到同类问题，应该走 V5 ship interaction gate，而不是去改 v4 或做临时 ferry patch。

今天的结论：V5 ship 的高松/小豆岛链路现在用真实数据可玩，选船后会从到达侧继续规划，runner 在到港、上船、到达接续点三个阶段都有可验证 marker。下一步如果继续 V5 主线，可以回到 highway/night bus 的第一批可玩线路；ship 交互已有回归测试兜底。
