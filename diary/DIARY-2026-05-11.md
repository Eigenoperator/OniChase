# DIARY - 2026-05-11

今天主要做 v4 的车次显示收尾，重点是山形新干线 `つばさ` 在 planning 2/3 中每个车号显示两次的问题。

问题本身不是源数据里真的多了一辆车，而是前端同时保留了两种候选：一条是原始的 `東京 -> 福島` 新干线共享段，另一条是我们为 mini-Shinkansen 直挂判定合成出来的 `東京 -> 山形/新庄` 贯通车。旧的去重 key 把首末站也写进比较条件，所以 `つばさ121 東京 -> 福島` 和 `つばさ121 東京 -> 新庄` 被视为两辆不同车，最终在玩家选车列表里重复出现。

修复方式是调整 `docs/v4.html` 的 boardable departure 去重逻辑：对新干线使用更符合玩家视角的 key，也就是同一线路选择、同一上车站、同一发车时间、同一公开车号、同一下一站，就应当被视为同一辆可乘车；当原始段和合成直挂段冲突时，优先保留合成后的贯通车。这样东京侧只显示 `つばさ121 東京 -> 新庄` 这一辆完整车，不再同时显示 `東京 -> 福島` 的碎片。

验证分两层做了。第一层是本地 route-choice 审计：`mini-shinkansen` 和 `known` 两个阶段都通过，`anomalyCount=0`。第二层是线上 GitHub Pages 探针，直接打开部署后的 `v4.html`，检查 `東京`、`福島`、`山形` 的 `山形新幹線` 选车列表，结果三个站的 `dupNums` 都是空数组。东京现在看到 8 条 `つばさ`，都是合成后的贯通车；福岛和山形保留了本来就只在支线段运行的车，同时不会把已配对的贯通车重复显示。

这次也再次确认了 mini-Shinkansen 的一个边界：新干线侧仍然不使用普通非新干线直挂的 portion picker，但游戏胜负和可乘坐判定应当把同号共享段与支线段当成同一辆贯通车处理。UI 上需要避免把源数据的物理切段暴露给玩家，这是 `つばさ`、`こまち` 这类车共同需要遵守的规则。
